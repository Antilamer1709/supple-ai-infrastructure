# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Terraform for the single `prod` environment of Supple AI in `eu-north-1`. It covers the Spring Boot backend (`../supple-ai-backend`) on Elastic Beanstalk with RDS PostgreSQL, the Angular back-office (`../supple-ai-frontend`) on S3 + CloudFront, and the catalog images (ingredient pictures) on a second S3 bucket + CloudFront distribution. Cognito handles auth, CloudWatch handles monitoring and AWS Budgets handles cost alerts. Sized for a few users at the lowest cost. `README.md` is the operator guide: step-by-step setup (new account, or an existing deployment after cloning), deploying, Google sign-in, "Before going live", custom domain and troubleshooting. `docs/monitoring.md` is the monitoring guide: where each metric, alarm and log lives, where to click in the CloudWatch console, the saved log queries, following one request, changing alert recipients.

Terraform manages infrastructure only. App code is deployed by `scripts/deploy-backend.sh` and `scripts/deploy-frontend.sh`, which read every value from `terraform output -raw`. Keep outputs and scripts in sync.

## Commands

```bash
export AWS_PROFILE=healthytech                   # `aws login --profile healthytech` first; Terraform reads the same profile
scripts/bootstrap-state.sh                       # once per account: state bucket + backend.hcl
terraform init -backend-config=backend.hcl
terraform fmt -recursive
terraform validate
terraform plan
terraform apply                                  # the user runs this, not Claude
terraform init -backend=false && terraform validate   # offline check, no AWS access needed
scripts/deploy-backend.sh                        # SKIP_TESTS=1 to skip the backend test suite
scripts/deploy-frontend.sh
```

- Use the `aws-mcp` tools (profile `healthytech`) for AWS lookups. Don't run the AWS CLI through Bash; the deploy and bootstrap scripts are for the user to run.
- Never run `terraform apply`/`destroy` or the deploy scripts without the user asking. They create billable resources or change production.
- The provider lock file is committed and pinned for macOS/Linux/Windows. After a provider bump, run `terraform providers lock -platform=darwin_arm64 -platform=darwin_amd64 -platform=linux_amd64 -platform=linux_arm64 -platform=windows_amd64`.

## Layout and conventions

- Flat root module, one file per concern: `network.tf`, `database.tf`, `cognito.tf`, `backend.tf` (Elastic Beanstalk, i.e. the *app* backend), `frontend.tf`, `media.tf` (catalog images: bucket + its own distribution), `budget.tf`, `monitoring.tf` (SNS alert topic, log transformer and saved queries, alarms, dashboard), `variables.tf` (naming locals at the top), `outputs.tf`, `versions.tf` (Terraform's S3 state backend and the provider).
- Names come from `local.name` (`supple-ai-prod`). Tags come from provider `default_tags`, so don't add per-resource tags except `Name`.
- State: S3 with `use_lockfile = true` (no DynamoDB). Bucket, key and region are in the gitignored `backend.hcl` written by `scripts/bootstrap-state.sh`. Never commit state, `*.tfvars` or `backend.hcl`. `terraform.tfvars.example` is the template; the real `terraform.tfvars` is kept in the state bucket (`s3://<state bucket>/terraform.tfvars`), and a newcomer's `terraform plan` must show no changes before anything is applied (README "Setup").
- Pinned versions: Terraform ≥ 1.11, `hashicorp/aws ~> 6.69.1`, `terraform-aws-modules/vpc/aws 6.7.3`.

## Design decisions to preserve

- **One CloudFront distribution for app and API.** `/api/*` goes to Beanstalk; everything else goes to the private S3 bucket through OAC. This makes every browser call same-origin. The backend has no CORS configuration and the frontend uses relative `/api` URLs. Don't add another distribution for the app or the API, or absolute API URLs.
- **Catalog images have their own distribution (`media.tf`), the one exception.** A private bucket (`${local.name}-media-<account>`, prefixes `ingredients/`, later `products/` and so on; one bucket for all public catalog media, a separate one for anything private) behind its own OAC and distribution, with stable unsigned URLs. The backend stores each upload under a new UUID key with `Cache-Control: public, max-age=31536000, immutable`, so no invalidation is ever needed; a replaced or deleted image may stay in edge caches until evicted. It's separate so the app distribution's 404 → `index.html` rule and same-origin setup stay untouched; it has no custom error responses, and its bucket policy grants only `s3:GetObject`, so a missing key is a 403. The browser loads `<img>` cross-origin without CORS, so neither the bucket nor the distribution has CORS rules. If a CSP is ever added to the app, its `img-src` must include the media domain.
- **SPA routing via a 404-only custom error response.** CloudFront error responses apply to the whole distribution, including `/api/*`. So only 404 is rewritten to `/index.html`, and the bucket policy grants CloudFront `s3:ListBucket` so S3 returns 404 (not 403) for missing keys. The backend's 403s must pass through. Its only 404 is GET-by-id with an unknown id, which the app doesn't call. Don't add a 403 rule. The user doesn't want Lambda or CloudFront Functions for now.
- **Origin lock.** The instance security group allows port 80 only from the `com.amazonaws.global.cloudfront.origin-facing` prefix list. The list weighs 55 of the 60-rule limit, so there's no room for another prefix-list rule. `DisableDefaultEC2SecurityGroup = true` keeps Beanstalk's world-open group off. There's no SSH; use Session Manager.
- **Single-instance Beanstalk, HTTP origin.** There's no load balancer for cost reasons. Without one, Beanstalk ignores the `/actuator/health` URL; it's set so it takes effect when an ALB is added. `README.md` "Before going live" lists the planned upgrades: ALB with auto scaling, the health check through it, a secret origin header, the Paid plan, 7-day backups.
- **Database password.** `manage_master_user_password = true`. Beanstalk injects the secret's `password` key as `SPRING_DATASOURCE_PASSWORD` (`environmentsecrets` namespace, `<arn>:password`), but only reads it at instance start or deploy. So `aws_secretsmanager_secret_rotation` turns rotation off. The `!` in RDS secret names was unverified against Beanstalk's validation; the README's troubleshooting section has the fallback.
- **Environment `lifecycle.ignore_changes = [version_label, solution_stack_name]`.** The deploy script changes the version and managed platform updates change the stack. The stack comes from a `most_recent` data source matching `Corretto 25` on AL2023.
- **Cognito.** One pool for admins and users with self sign-up. Admins are members of the `admin` group, added by hand in the console; the backend maps groups to `ROLE_<GROUP>` and requires exactly `admin`. Managed Login v2 with Cognito's default branding. Google is the built-in social provider, created only when both Google variables are set; generic OIDC would get only 50 free MAUs. Every social provider maps its avatar to Cognito's standard `picture` attribute, which is the only avatar source the app reads; a provider without one (Apple, for example) leaves `picture` unmapped and its users get the default avatar. Callback/logout URLs are the CloudFront address and `http://localhost:4200`. The **mobile app client** (`aws_cognito_user_pool_client.mobile`) is created ahead of the app so the mobile developer never touches AWS: public, code + PKCE plus native `USER_AUTH`/SRP, redirects `formulated://callback` / `formulated://signout` (`local.mobile_url_scheme`), 60-min access/ID and 90-day refresh tokens, its own default Managed Login branding. Its id goes to Beanstalk as `COGNITO_MOBILE_CLIENT_ID`; the backend counts its tokens as app activity and all others as back office. Don't pass the back-office client's id instead: the back-office client depends on CloudFront, CloudFront on the environment, so that's a cycle. `output "cognito_mobile_client_id"` feeds `../supple-ai-backend/docs/mobile-client.md`.
- **The backend reads the user pool** for the admin Users screen with `ListUsers` and `AdminListGroupsForUser`, granted to the instance role by the `ReadUserPool` statement in `backend.tf` (the pool ARN only). It derives the pool id and region from `COGNITO_ISSUER_URI`, so no extra variable is passed. Without the permission, that screen gets a 503.
- **The backend writes catalog images** with `s3:PutObject` and `s3:DeleteObject` on the media bucket's objects only (the `WriteMedia` statement in `backend.tf`); it never reads them back, the media distribution serves them. Four Beanstalk variables are a cross-repo contract with the backend's `supple.media.*` properties: `SUPPLE_MEDIA_BUCKET`, `SUPPLE_MEDIA_BASE_URL` (`https://<media distribution>`, no trailing slash), `SUPPLE_MEDIA_ENDPOINT` (`https://s3.<region>.amazonaws.com`) and `SUPPLE_MEDIA_PATH_STYLE_ACCESS=false`. The backend's defaults are the local S3Mock with path-style access, so production must set all four, the real regional endpoint included.
- **Monitoring stays in CloudWatch's always-free tier ($0, also on the Paid plan).** The budget is 10 alarm metrics (all 10 used; the heap alarm's `used ÷ max` math counts twice), 10 custom metrics (6 used: Beanstalk's `ApplicationRequests5xx` and `ApplicationLatencyP95` via the `ConfigDocument` setting, the backend's three Micrometer gauges in `SuppleAI/Backend`, and the `ErrorLogLines` log metric filter) and 3 dashboards (1 used). Add an alarm or metric only after removing one, and keep the counts in the `monitoring.tf` header and `docs/monitoring.md` current. No tracing, RUM, Synthetics, Container Insights or Enhanced Monitoring; an outside uptime probe is deferred to the load balancer ("Before going live").
  - Every alert goes to `alert_emails` (1–10 addresses, the Budgets limit) through one SNS topic, `${local.name}-alerts`. Beanstalk events use it too (`Notification Topic ARN`), and the budget emails the list directly. All alarms set `ok_actions`.
  - No CloudFront alarm: CloudFront's metrics exist only in us-east-1, an alarm can only notify an SNS topic in its own region, and the SCP denies SNS in us-east-1 (the first apply failed on `CreateTopic` there). Its slot holds the `api-slow` alarm on Beanstalk's `ApplicationLatencyP95`. The dashboard still graphs CloudFront from us-east-1. A Route 53 health check is ruled out for the same reason.
  - Beanstalk reports some settings in its own form, so `backend.tf` matches it: `ConfigDocument` is a literal string in Beanstalk's key order (`jsonencode` sorts keys), and `Subnets` is sorted. `ServiceRoleForManagedUpdates` is never reported back, so every plan shows it being added; the user chose to keep it and document it (README "Setup", B step 6).
  - The backend's metric names are a cross-repo contract: Micrometer publishes gauges as `<meter>.value` (`supple.jvm.heap.used.value`, `supple.jvm.heap.max.value`, `hikaricp.connections.pending.value`), the backend allowlists exactly those meters and drops their tags, and the instance role may `PutMetricData` only in the `SuppleAI/Backend` namespace. The backend's export is switched on by `MANAGEMENT_CLOUDWATCH_METRICS_EXPORT_ENABLED=true` and its JSON logs by `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs`, both set in `backend.tf`.
  - Beanstalk's rsyslog prefixes every app line (`Nov  1 10:00:00 ip-… web[pid]: {json}`) and cuts it at 8 KB (the backend caps stack traces at 4,096 characters, root cause first, to stay under). The prefix hides the JSON from Logs Insights and from JSON metric-filter patterns. The `ErrorLogLines` filter therefore reads the original line with the regex `%level...ERROR%`, matching `"level":"ERROR"` (ECS nests the level under `log`; metric-filter regexes reject `"`, and the first apply failed on it). For queries, `aws_cloudwatch_log_transformer.backend` (grok, then parseJSON) turns every key into a Logs Insights field. The saved queries (`aws_cloudwatch_query_definition`, folder `supple-ai-prod`) read those fields, the backend's MDC keys (`requestId`, `path`, `route`, `status`, `durationMs`, `userSub`) and ECS's `log.level` and `error.*`. The transformer is part of the ingestion price and leaves the metric filter on the original line (`apply_on_transformed_logs` stays false). The user chose it over shipping a `.platform` rsyslog hook, which would mean switching the deploy to a zip bundle. Terraform's saved queries can't take parameters, so the per-id ones carry a `REPLACE-WITH-…` placeholder.
  - Alarms address the instance by its Auto Scaling group (`autoscaling_groups[0]`), which survives platform updates, and the database by its identifier.
- **The apps hold only the Cognito IDs.** Frontend `src/environments/environment.ts` and the backend `application.yaml` issuer default. They contain `6plp3eqqvjlf3u7mav5q7b5mh6%` placeholders until the first apply. `deploy-frontend.sh` refuses builds whose IDs don't match `terraform output`.

## AWS account constraints

- The `healthytech` account is a "Sign up for AWS (new)" project account on the **Free plan**. AWS-managed SCPs allow regional resources only in `eu-north-1`; global services go through `us-east-1`, and ACM, CloudFront, Budgets and IAM are allowed there. SNS is denied in `us-east-1`. Spot, Lambda@Edge, Organizations changes and IAM `*Provider*` actions are denied. Roles under `/managed/` are AWS's; don't touch them.
- The Free plan allows only free-tier instance types (t3/t4g micro/small, c7i-flex.large, m7i-flex.large; `db.t3.micro`/`db.t4g.micro` for RDS). It reportedly rejects RDS backup retention above 1 day and in-place EC2 resizes. The account closes when the credits run out or the plan ends (2027-04-15 as of 2026-10-19), unless upgraded in AWS Settings. Check with `freetier GetAccountPlanState` through aws-mcp.
- EC2 vCPU quota is 5: one t4g.small (2 vCPU), plus a second one temporarily during managed platform updates.
- Budgets must use `include_credit = false`. On the Free plan, usage net of credits is always $0.
